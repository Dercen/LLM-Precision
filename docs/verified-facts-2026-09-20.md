REC: Toolchain section of the plan (verified 2026-09-20):

1. Python: standardize on 3.12 (requires-python = ">=3.12,<3.14", .python-version = 3.12, installed by `uv python install 3.12`). Do NOT use the machine's 3.10 (EOL October 2026) and do not target 3.14 yet (flash-attn/vLLM/prebuilt kernels lag). 3.13 (already installed) is fully supported by every library in the stack and may be used if the user prefers; the uv lock will cover both.

2. PyTorch: pin torch==2.13.0 in the lock (most ecosystem-aligned: torchao 0.18.0 release CI, llm-compressor 0.13.0 cap, vLLM 0.29.0 pin), with a documented path to 2.14.0 (current stable, 2026-09-02) if llm-compressor/vLLM are never used. Windows laptop gets the +cpu wheel from https://download.pytorch.org/whl/cpu; the Linux server gets +cu126 (older drivers) or +cu130 (newer drivers) - decide after running nvidia-smi on the server; cu128 no longer exists for these versions; cu132 is also available. Use SDPA attention (default), not flash-attn; treat torch.compile as server-only and optional.

3. Package manager: uv 0.12.17. One pyproject.toml with [[tool.uv.index]] entries (pytorch-cpu, pytorch-cu126, pytorch-cu130, explicit=true) and [tool.uv.sources] markers/extras so the same universal uv.lock resolves CPU wheels on Windows and CUDA wheels on Linux. Set UV_PROJECT_ENVIRONMENT, UV_CACHE_DIR and HF_HOME to a non-OneDrive path (e.g. C:\ml\research-env, C:\ml\uv-cache, C:\ml\hf-cache) and put .venv/, *.lock caches, results/ artifacts in .gitignore; on the server use $SCRATCH equivalents. Provide SLURM sbatch and plain-SSH nohup launchers; the code itself must be device-agnostic (device = cuda if available else cpu).

4. Library pins: transformers==5.17.0, datasets==5.0.1, accelerate==1.15.0, optimum==2.3.0, gptqmodel==7.5.0 (install with --no-build-isolation; source-only sdist; needs ninja; Windows uses the pure Torch kernel), bitsandbytes==0.50.2 (has Windows CPU/AVX2 wheels), hqq==0.2.8.post1 (pure-PyTorch, arbitrary 2/3/4/8-bit RTN-style on-the-fly - ideal for the bit sweep on CPU), torchao==0.18.0 (pure-Python wheel on Windows), lm_eval==0.4.13 (optional cross-check of perplexity). REC: Design principle for the plan: a perplexity-vs-bit-width study only needs fake quantization (quantize -> dequantize back to fp16/bf16 -> normal matmul). None of the kernel libraries are required for that, and the kernel libraries are exactly where the Windows/CPU/Triton problems live. So the framework should implement the core algorithms itself in pure PyTorch and treat third-party libraries as optional, pluggable reference backends.

1. Core (Tier 0, runs everywhere): implement RTN (per-channel and per-group, symmetric/asymmetric, 2/3/4/8-bit) and GPTQ (Hessian from calibration activations, per-layer OBQ update; the reference implementation is ~300 lines) in pure torch inside the repo; optionally add AWQ-style activation-aware scaling and SmoothQuant scaling as extra passes since they are also just weight/scale transforms. This gives identical behaviour on Windows CPU (opt-125m) and Linux CUDA (OPT-6.7b/Llama), arbitrary bit widths (3-bit and 2-bit are not available in bitsandbytes and only partially in torchao), zero Triton dependency, and no reliance on Windows wheels. Perplexity evaluator (wikitext2 / C4 / PTB, 2048-token windows) is shared by every backend.

2. Tier 1 reference backends that are verified to work on Windows CPU today: bitsandbytes 0.50.2 (official win_amd64 + CPU wheels; LLM.int8 and NF4/FP4 on CPU with AVX2 — the Ryzen 5825U qualifies) and HQQ 0.2.8.post1 (pure PyTorch, 1–8 bits, data-free; install with DISABLE_CUDA=1). Both are usable through transformers quantization_config with device_map='cpu'.

3. Tier 2 reference backends for the Linux CUDA server only: GPTQModel 7.5.0 (the transformers-official GPTQ backend; also AWQ; sdist + ninja JIT compile, needs a C/C++ toolchain; torch>=2.8, transformers>=5.14, hard dep on torchao>=0.16 and numpy==2.2.6) and llm-compressor 0.13.0 (GPTQ/AWQ/SmoothQuant/AutoRound; output loads via compressed-tensors). Because llm-compressor pins transformers<=5.14.1 and torch<=2.13.0 while GPTQModel needs transformers>=5.14.0 and torch is now 2.14.0, put llm-compressor in its own venv (transformers 5.14.x, torch 2.13.0) or pin the whole server env to that intersection. torchao 0.18.0 is fine on Linux for int8/int4 weight-only RTN (GPTQ/AWQ there are prototypes only) but has no Windows wheels — keep it out of the Windows path (mark GPTQModel's Windows support as 'claimed, unverified' and gate it behind a feature flag).

4. Do not use: AutoGPTQ (archived 2025-04-11, dropped by transformers), AutoAWQ (archived 2025-05-11, hard-requires triton so it will not even pip-install on Windows, incompatible with transformers 5.x), optimum-quanto (maintenance mode since 2025-03; adds nothing over HQQ/bitsandbytes; unverified with transformers 5.17). Triton: irrelevant on the CPU laptop and automatic on Linux CUDA; only if a Windows NVIDIA box appears, `pip install triton-windows` (Ampere+ GPU).

5. Environment pins for the plan: Python 3.13 locally is fine (torch 2.14.0 has cp313 win_amd64 CPU wheels; all Tier 0/1 packages support >=3.10) — use the same minor on the server and avoid 3.14 for now. Baseline: torch 2.14.0 (CPU wheel on Windows from PyPI, CUDA wheel on Linux from download.pytorch.org), transformers 5.17.0, datasets, accelerate, bitsandbytes 0.50.2, hqq 0.2.8.post1 (DISABLE_CUDA=1). - [confirmed] accelerate device_map='auto' + CPU offload behaviour on Windows
    accelerate 1.15.0 (2026-09-09, Python >=3.10) is pure Python. device_map='auto' fills GPU(s) first, then CPU RAM, then disk (memmapped .dat files in offload_folder; bf16 stored as int16); hooks move offloaded weights to the GPU right before each layer's forward and free them after, with no prefetching, inference-only, and everything under torch.no_grad — so CPU offload is functional but slow. Windows-specific evidence: issue #4280 (2026-09-19) reports dispatch_model with CPU+disk offload running on Windows 11 build 26200, Python 3.13.13, torch 2.14.0+cpu, accelerate 1.16.0.dev0 — the code path works there (the report is an O(N*M) init slowdown, PR #4281). Issue #3041 (Windows 10, accelerate 0.33.0) is an infer_auto_device_map algorithm issue, not Windows-specific: once it spills to CPU it never places later modules back on GPU and it reserves the largest layer per device, so heterogeneous models can end up entirely on CPU; still open. Practical advice: set max_memory explicitly, use absolute paths for offload_folder, and do not rely on multi-GPU/torch.distributed on Windows (NCCL unavailable).
